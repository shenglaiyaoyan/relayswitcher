## 2. 核心方案与取舍

**目录源架构(US-01/02 的地基)** — 三选一:

- **A. 双源 + 用户级覆盖(采用)**:内置资源目录保持只读快照;「提取」产出用户级目录文件;`settings.catalogMode: 'builtin' | 'extracted'`;自定义模型在**部署时动态合并**进 whichever 源,不落盘改源文件。
  理由:内置快照永远可回退;提取产物独立可删;合并逻辑集中在切换链路,预检统一覆盖。
- B. 目录全动态数据库化 — 过度设计,否决。
- C. 允许直接编辑目录 JSON — 高危(坏目录炸 Codex 已实证),否决;仅保留派生式自定义模型。

**数据流**:`catalogMode → 读源(builtin 资源 | userData/catalogs/extracted-*.json) → 合并 customModels → schema 预检(沿用 v1.4.6) → 原子部署`。

**提取器设计**:独立模块 `electron/lib/catalog-extract.js`,纯函数核心(注入 buffer → {catalog, report}),IO(找 exe/读文件)在 main.js 薄壳——便于单测(伪造含锚点的 buffer 即可,不需要真 2GB 二进制)。

**兜底策略**:缺 base_instructions 的条目 → 用 gpt-5.5 全文(与 CockpitTools 生产配置一致,v1.4.6 已实证);report 里逐条标注 `patched: [slugs]`。

**CI**:windows-latest + Node 20;`npm ci → node --test → vite build`;electron-builder 构建 artifact(不自动发 Release,发布仍手动把关)。冒烟(electron --smoke)依赖 GUI 会话,CI 里跳过,仅本地跑。
